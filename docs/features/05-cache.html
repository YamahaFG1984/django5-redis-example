Cache-Aside 模式

为什么是「删除缓存」而不是「更新缓存」

三大经典问题

问题现象对策代码位置
穿透 Penetration请求的数据根本不存在（比如有人遍历随机 URL），缓存永远不会命中，每次都查数据库把「不存在」也缓存起来：存一个 MISSING 标记，TTL 60 秒get_or_load 中 value is None 分支
击穿 Breakdown一个热点 Key 过期的瞬间，大量并发请求同时未命中，同时查数据库分布式锁：只让一个请求去查数据库，其余请求等待后读缓存RedisLock + get_or_load
雪崩 Avalanche大量 Key 在同一时刻过期（比如启动时一起写入），数据库同时承受大量回源过期时间加随机抖动，把过期时刻分散开jitter()

击穿：分布式锁

雪崩：随机抖动

分布式锁的细节

加锁很简单：SET key token NX PX 10000。容易出错的是释放锁：

class RedisLock:
    """最简单的分布式锁：SET key token NX PX timeout"""

    def __init__(self, name, timeout=10):
        self.key = K.lock(name)
        self.timeout_ms = int(timeout * 1000)
        # 每个持有者一个随机 token，防止误删别人的锁
        self.token = uuid.uuid4().hex

    def acquire(self):
        return bool(
            get_redis().set(self.key, self.token, nx=True, px=self.timeout_ms)
        )

    def release(self):
        return get_redis().eval(RELEASE_LOCK_SCRIPT, 1, self.key, self.token) == 1

ⓘ Lua 脚本为什么是原子的

Redis 用单线程执行命令。一个 Lua 脚本在执行期间，其他客户端的命令都要等待，所以脚本内部的 GET 和 DEL 之间不会插入别的命令。redis-py 自带的 r.lock() 也是这样实现的。这里手写一遍是为了看清原理。

核心：get_or_load

def get_or_load(key, loader, timeout=300, lock_wait=2.0):
    """
    读缓存；未命中时调用 loader() 从数据库加载并写回缓存。
    loader 返回 None 表示数据不存在。
    """
    value = cache.get(key)
    if value is not None:
        return _unwrap(value)

    lock = RedisLock(f'cache:{key}')
    if lock.acquire():
        try:
            # 双重检查：等锁期间，可能已经有别的请求写好了缓存
            value = cache.get(key)
            if value is None:
                value = loader()
                if value is None:
                    cache.set(key, MISSING, MISSING_TIMEOUT)
                else:
                    cache.set(key, value, jitter(timeout))
                return value
            return _unwrap(value)
        finally:
            lock.release()

    # 没抢到锁：说明有别的请求正在加载，稍等片刻再读缓存
    deadline = time.monotonic() + lock_wait
    while time.monotonic() < deadline:
        time.sleep(0.05)
        value = cache.get(key)
        if value is not None:
            return _unwrap(value)
    # 等太久了（持锁的请求可能出错了），直接查数据库兜底，不写缓存
    return loader()

⚠ 缓存 QuerySet 时要先 list()

QuerySet 是惰性的。直接把 QuerySet 放进缓存，pickle 时会触发查询，但很容易误以为缓存的是「查询结果」。用 list() 先求值，存进去的就是确定的 Post 列表。

用信号让缓存失效

@receiver(pre_save, sender=Post)
def post_before_save(sender, instance, **kwargs):
    # step-05 记住修改前的文章：如果 slug 或发布日期变了，旧的缓存 key 也要删
    instance._old = Post.objects.filter(pk=instance.pk).first() if instance.pk else None

文章的 slug 或发布日期变化后，缓存 Key 也变了。所以在 pre_save 里先取出修改前的记录，保存后把新旧两个 Key 都删掉。

边界与思考

⚠ 本实现的取舍
  • 先更新数据库再删缓存，仍然有很小的不一致窗口：读请求 A 未命中，从数据库读到旧值；写请求 B 更新数据库并删除缓存；然后 A 才把旧值写入缓存。常见对策是「延迟双删」（过几百毫秒再删一次），或者订阅数据库 binlog 来删除缓存。本项目依靠 TTL 兜底。
  • 锁可能在 loader 执行完之前过期：如果查询超过 10 秒，锁会自动释放，另一个请求也会去查数据库。生产环境的做法是在持锁期间定时续期（看门狗），或者使用 Redisson、Redlock 等方案。
  • pickle 缓存模型对象：部署新代码时如果模型字段变了，旧缓存反序列化可能出错。可以在发布时修改 CACHES['default']['VERSION']。

思考题

  1. 相似文章缓存只靠 TTL 过期。如果要做到给文章修改标签后立即生效，需要删除哪些 Key？
  2. Django 还有 {% cache 600 sidebar %} 模板片段缓存和 @cache_page 整页缓存。为什么本项目不直接对文章页使用 @cache_page？（提示：浏览量、登录状态）
  3. 如果缓存的是「热点文章列表」，有没有办法让它永不过期，又能定期刷新？（提示：逻辑过期 + 后台刷新）
