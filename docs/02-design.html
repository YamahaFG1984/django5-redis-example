1总体架构

几个关键决策：

  • 两个逻辑库分开使用。db0 存业务数据（计数、关系、榜单等）；db1 给 Django 缓存框架用。原因是 cache.clear() 执行的是 FLUSHDB，如果和业务数据放在同一个库，清缓存会把点赞、签到数据一起删掉。
  • 两套客户端。业务数据用 redis-py 直接操作，这样能用到 ZSET、Bitmap、Stream 等全部命令。缓存走 Django 自带的 RedisCache 后端，它会自动处理序列化和 Key 前缀。
  • 耗时任务交给后台进程。通知这类任务通过 Redis Stream 交给独立的 worker 进程处理，不阻塞 Web 请求。

3Key 命名规范

3.1 规则

  1. 格式：{前缀}:{实体}:{ID}:{属性}，用冒号分层。RedisInsight 等工具会按冒号把 Key 显示成树。
  2. 统一前缀 blog:（可通过 REDIS_KEY_PREFIX 修改）。多个项目共用一个 Redis 时不会冲突。
  3. 所有 Key 都定义在 redis_keys.py，业务代码里不出现手写的 Key 字符串。这样一个文件就能看到 Redis 里全部数据的结构，改名也只需要改一处。
  4. 按时间分片的 Key 把日期放在最后，例如 :day:20261030，过期清理靠 TTL。
  5. 临时 Key（计算中间结果、去重标记、锁）一定要设置 TTL。

关于模式 C

教学项目为了突出 Redis 的用法，把点赞、关注等数据只存在 Redis 里，并在 docker compose 中开启了 appendonly yes（AOF，每秒刷盘），最多丢失约 1 秒的数据。生产环境中这类用户资产通常会同时写入数据库（或者通过 Stream 异步写入），Redis 只负责高频读取。

6性能约定

不要这样写

# 列表页 10 篇文章 → 10 次网络往返
for post in posts:
    post.views = r.get(f'blog:post:{post.id}:views')

应该这样写

# 1 次往返拿到全部
keys = [K.post_views(p.id) for p in posts]
for post, v in zip(posts, r.mget(keys)):
    post.views = int(v or 0)
  • 批量读用 MGET 或 pipeline，一次请求内的 Redis 往返次数要固定，不能随数据量增长。
  • 多条写命令用 pipeline 合并；需要「先判断再写」的逻辑用 Lua 脚本，保证原子性。
  • 不要用 KEYS *，会阻塞 Redis。需要遍历时用 SCAN（见 sync_post_views，用 dirty 集合避免遍历）。
  • 大集合控制大小：时间线 ZREMRANGEBYRANK 截断到 500，收件箱 LTRIM 到 50，Stream 用 MAXLEN ~ 截断。

8测试策略

  • 测试连接真实的 Redis（不用 mock），这样测到的就是真实命令的行为；使用 db15（业务）和 db14（缓存），不会影响开发数据。
  • RedisTestCase 基类在每个用例开始前执行 FLUSHDB，保证用例之间互不影响。
  • 服务层测试直接调用 service 函数；视图层测试用 Django Client 走完整请求，再到 Redis 里检查数据。

10风险与降级

风险影响本项目的处理生产环境建议
Redis 宕机所有依赖 Redis 的功能报错教学项目将 Redis 视为强依赖在 service 层捕获 redis.ConnectionError：计数类直接跳过，展示类回落到数据库查询
Redis 数据丢失计数、关系丢失AOF；浏览量回写数据库；索引可以 rebuild主从复制 + 哨兵 / 集群；用户资产双写数据库
大 Key阻塞、迁移慢时间线、收件箱、Stream 都限制了长度定期用 redis-cli --bigkeys 巡检
热 Key单分片压力大—本地缓存 + Key 打散
