Step 12 · 消息队列

评论通知：用 Stream 消费组做可靠的异步任务

有人评论时通知文章作者。Web 请求只往 Stream 里写一条事件就返回，由后台进程以消费组的方式读取、处理、确认。进程崩溃后，没确认的消息会被其他消费者接管，不会丢失。

git checkout step-12-notifications STREAMLISTSTRING

本章目标

  • 比较 LIST、Pub/Sub、Stream 三种消息队列
  • 理解消费组、PEL 和 ACK
  • 用 XAUTOCLAIM 接管崩溃消费者的消息
  • 用 transaction.on_commit 保证事件在提交后才发出

场景分析

PRD F10：评论提交后立即返回，不被通知逻辑拖慢；侧边栏显示未读数；后台进程崩溃重启后，未处理的消息不丢失；每个作者最多保留 50 条通知。

「通知」这一类工作（发站内信、发邮件、推送）有几个共同点：可能很慢（发邮件要连 SMTP）、可能失败、不需要在请求里同步完成。所以应该交给后台进程，Web 进程和后台进程之间需要一个消息队列。

def stream_comments():
    """STREAM  评论事件，约保留最近 1 万条；消费组 notifier"""
    return _k('stream', 'comments')


def user_inbox(user_id):
    """LIST  站内信（JSON 字符串），最新的在左边，最多 50 条"""
    return _k('user', user_id, 'inbox')


def user_unread(user_id):
    """STRING  未读通知数"""
    return _k('user', user_id, 'unread')

端到端流程

⚠ 为什么要 transaction.on_commit

如果在 post_save 里直接 XADD，事件可能在数据库事务提交之前就被 worker 读到，worker 去查这条评论时查不到。on_commit 保证事务提交成功后才发事件；事务回滚的话也不会发。在 TestCase 中要用 captureOnCommitCallbacks(execute=True) 才能触发这些回调。

消费者

def ensure_group():
    """创建消费组（已存在则忽略）。id='0' 表示从 Stream 的第一条消息开始消费。"""
    try:
        get_redis().xgroup_create(K.stream_comments(), GROUP, id='0', mkstream=True)
    except redis.ResponseError as exc:
        if 'BUSYGROUP' not in str(exc):
            raise
def process_batch(consumer, count=10, block_ms=5000):
    """处理一批消息，返回处理的条数。"""
    r = get_redis()
    stream = K.stream_comments()
    # 1. 先接管其他消费者领取后长时间没有 ACK 的消息（消费者崩溃了）
    _, messages, _ = r.xautoclaim(
        stream, GROUP, consumer, min_idle_time=CLAIM_IDLE_MS, start_id='0-0', count=count
    )
    # 2. 没有要接管的，就读取新消息：">" 表示从未投递给本组任何消费者的消息
    if not messages:
        response = r.xreadgroup(GROUP, consumer, {stream: '>'}, count=count, block=block_ms)
        messages = response[0][1] if response else []

    for message_id, fields in messages:
        if fields:
            handle_event(fields)
        # 3. 处理完才 ACK；ACK 之前崩溃的话，消息还在待处理列表（PEL）中，会被重新处理
        r.xack(stream, GROUP, message_id)
    return len(messages)
def handle_event(fields):
    """处理一条评论事件：给文章作者发一条站内信。"""
    comment = (
        Comment.objects.select_related('post')
        .filter(id=int(fields['comment_id']))
        .first()
    )
    if comment is None:
        return False   # 评论已经被删除，直接丢弃
    post = comment.post
    message = json.dumps({
        'post_title': post.title,
        'url': post.get_absolute_url(),
        'name': comment.name,
        'excerpt': comment.body[:80],
        'created': comment.created.isoformat(),
    })
    pipe = get_redis().pipeline()
    pipe.lpush(K.user_inbox(post.author_id), message)
    pipe.ltrim(K.user_inbox(post.author_id), 0, INBOX_SIZE - 1)
    pipe.incr(K.user_unread(post.author_id))
    pipe.execute()
    return True

Worker 命令与部署

def handle(self, *args, consumer, once, **options):
    notifications.ensure_group()
    self.stdout.write(f'notify_worker started as "{consumer}"')
    try:
        while True:
            handled = notifications.process_batch(consumer)
            if handled:
                self.stdout.write(f'handled {handled} event(s)')
            if once:
                break
    except KeyboardInterrupt:
        self.stdout.write('bye')

边界与思考

⚠ 本实现的取舍
  • 至少一次，不是恰好一次：worker 在 LPUSH 之后、XACK 之前崩溃，消息会被重新处理，作者收到两条相同的通知。要做到幂等，可以用 SET notified:{comment_id} 1 NX EX 86400 去重（第 3 章的防刷技巧）。
  • 一直失败的消息：如果某条消息每次处理都抛异常，会被不断接管、重试。XPENDING 返回的投递次数（delivery count）可以用来判断，超过 N 次就转移到「死信」Stream 并 ACK。
  • MAXLEN ~ 截断：如果 worker 停了很久，积压超过约 1 万条，最早的消息会在被消费前被截断。生产环境需要监控消费组的 lag。
