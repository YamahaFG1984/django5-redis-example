Step 08 · Feed 流

关注与时间线：写扩散 Feed 流与游标分页

关注作者后，在「我的时间线」里按时间看到他们的新文章，这就是 Feed 流。这一章用 SET 存关注关系（还可以求交集得到共同关注），用 ZSET 做发件箱和收件箱，实现推模式，再用分数游标解决翻页时数据重复的问题。

git checkout step-08-follow-timeline SETZSET

1场景分析

PRD F6：关注 / 取消关注作者；作者发布文章后，粉丝的时间线里立刻出现；新关注时补上作者最近的文章，取消关注后移除；翻页时有新文章发布也不重复、不遗漏；显示共同关注。

用 SQL 读时间线是这样的：

SELECT * FROM blog_post
WHERE author_id IN (SELECT followee_id FROM follows WHERE follower_id = 3)
  AND status = 'PB'
ORDER BY publish DESC LIMIT 10 OFFSET 20;

关注的人越多，IN 子查询越大；每次刷新时间线都要执行一遍排序。Feed 流有两种基本思路，选择取决于读写比例。

2推模式还是拉模式

拉模式（读扩散）推模式（写扩散）推拉结合
发布成本O(1)O(粉丝数)普通作者推，大 V 不推
读取成本O(关注数 × log)O(log N)，读一个 ZSET读收件箱 + 拉大 V 发件箱
存储只存一份每个粉丝存一份 ID介于两者之间
适合关注数少、粉丝很多读多写少，粉丝数可控微博、Twitter 这类大型社区

博客是典型的读多写少，作者的粉丝数也不会太大，所以选择推模式。收件箱只存文章 ID，内容按 ID 从数据库批量读取。

def user_following(user_id):
    """SET  我关注的人"""
    return _k('user', user_id, 'following')


def user_followers(user_id):
    """SET  关注我的人（粉丝）"""
    return _k('user', user_id, 'followers')


def user_posts(user_id):
    """ZSET  作者的发件箱：member = 文章 ID，score = 发布时间戳"""
    return _k('user', user_id, 'posts')


def timeline(user_id):
    """ZSET  用户的收件箱（时间线），最多保留 500 条"""
    return _k('timeline', user_id)

7代码实现

7.1 关注

def follow(follower_id, followee_id):
    """关注。返回 True 表示新关注。"""
    if follower_id == followee_id:
        raise ValueError("You can't follow yourself.")
    r = get_redis()
    pipe = r.pipeline()
    pipe.sadd(K.user_following(follower_id), followee_id)
    pipe.sadd(K.user_followers(followee_id), follower_id)
    added, _ = pipe.execute()
    if added:
        _backfill(r, follower_id, followee_id)
    return bool(added)
def _backfill(r, user_id, author_id):
    """新关注一个作者：把他最近的文章补进我的时间线。"""
    recent = r.zrevrange(K.user_posts(author_id), 0, BACKFILL - 1, withscores=True)
    if recent:
        pipe = r.pipeline()
        pipe.zadd(K.timeline(user_id), dict(recent))
        pipe.zremrangebyrank(K.timeline(user_id), 0, -TIMELINE_MAX - 1)
        pipe.execute()

7.2 推送

def publish(post):
    """文章发布（或更新）时：写入作者发件箱，再推送到每个粉丝的收件箱。"""
    r = get_redis()
    score = post.publish.timestamp()
    r.zadd(K.user_posts(post.author_id), {post.id: score})

    pipe = r.pipeline(transaction=False)
    # SSCAN 分批遍历粉丝，粉丝很多时也不会一次把 Redis 卡住
    for i, follower_id in enumerate(
        r.sscan_iter(K.user_followers(post.author_id), count=FANOUT_BATCH), 1
    ):
        pipe.zadd(K.timeline(follower_id), {post.id: score})
        pipe.zremrangebyrank(K.timeline(follower_id), 0, -TIMELINE_MAX - 1)
        if i % FANOUT_BATCH == 0:
            pipe.execute()
    pipe.execute()
SSCAN 和 SMEMBERS

SMEMBERS 一次返回整个集合，粉丝有几十万时，这一条命令会阻塞 Redis 一段时间，返回的数据量也很大。sscan_iter 在内部反复调用 SSCAN cursor COUNT 1000，每次只取一小批，期间其他客户端的命令可以穿插执行。

7.3 读取时间线

def get_timeline(user_id, before=None, count=10):
    """
    游标分页读取时间线。before 是上一页最后一条的 score（发布时间戳），
    返回 (文章列表, 下一页的 before 或 None)。
    """
    # "(" 表示开区间：不包含 before 本身，避免上一页最后一条重复出现
    max_score = f'({before}' if before is not None else '+inf'
    pairs = get_redis().zrevrangebyscore(
        K.timeline(user_id), max_score, '-inf', start=0, num=count, withscores=True
    )
    ids = [int(member) for member, _ in pairs]
    posts = Post.published.in_bulk(ids)
    next_before = pairs[-1][1] if len(pairs) == count else None
    return [posts[i] for i in ids if i in posts], next_before

7.4 信号

@receiver(post_save, sender=Post)
def post_saved(sender, instance, **kwargs):
    # step-05 删除缓存（而不是更新缓存），下次读取时自然会重新加载
    cache_service.invalidate_post(instance)
    if getattr(instance, '_old', None) is not None:
        cache_service.invalidate_post(instance._old)
    cache_service.invalidate_sidebar()

    # step-09 更新标签倒排索引（下线的文章会被移出）
    recommend.index_post(instance)
    # step-11 更新标题联想索引（标题可能改过，旧的要删掉）
    search.index_title(instance, getattr(instance, '_old', None))

    if instance.status == Post.Status.PUBLISHED:
        # step-08 推送到粉丝的时间线
        timeline.publish(instance)
    else:
        # step-04 下线的文章从排行榜移除
        ranking.remove_post(instance.id)
        # step-08 从时间线移除
        timeline.unpublish(instance)

7.5 重建发件箱

发件箱的数据可以从数据库完整推导出来（设计文档中的「模式 A」），所以提供了 python manage.py rebuild_redis_index。后面的章节也会往这个命令里添加各自的重建逻辑。

def rebuild_outboxes():
    """从数据库重建所有作者的发件箱（Redis 数据丢失或首次上线时使用）。"""
    r = get_redis()
    pipe = r.pipeline(transaction=False)
    for post in Post.published.only('id', 'author_id', 'publish'):
        pipe.zadd(K.user_posts(post.author_id), {post.id: post.publish.timestamp()})
    pipe.execute()

9边界与思考

本实现的取舍
  • 推送是同步执行的：在保存文章的请求中完成。粉丝有几万人时，Admin 保存文章会变慢。应该把推送交给后台进程，第 12 章的 Stream 消息队列就可以用来做这件事。
  • score 相同的文章：游标用开区间，如果两篇文章的发布时间完全相同（精确到微秒），翻页可能漏掉一篇。严格的做法是用「score + member」组合作为游标。
  • 只保留 500 条：翻到 500 条以后就没有数据了。可以在收件箱读完后改用拉模式，从关注的作者发件箱里继续取。
思考题
  1. 一位作者有 100 万粉丝（大 V），推模式会写 100 万次。推拉结合的方案中，读时间线的代码应该怎么改？（提示：ZUNIONSTORE 收件箱和大 V 的发件箱）
  2. 长期不登录的「僵尸粉」也会收到推送。怎么只推送给最近活跃的粉丝？
  3. unfollow 中，如果作者发件箱很大，ZREM timeline *post_ids 会很慢。有没有更好的办法？
