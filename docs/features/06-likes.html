Step 06 · 集合

点赞：用 SET 和 ZSET 存同一份关系

点赞看起来简单，但要同时回答「这篇文章多少赞」「我赞过没有」「我赞过哪些文章」三个问题。这一章用 SET 存「文章 → 点赞用户」，用 ZSET 存「用户 → 点赞过的文章」，再用一个 pipeline 把列表页需要的数据一次取回。

git checkout step-06-likes SETZSET

1场景分析

PRD F4 的要求可以归纳为下面这些读写操作：

操作频率需要的能力
点赞 / 取消点赞中幂等：重复点赞不会重复计数
文章点赞数极高（列表页每篇都显示）O(1) 取数量
我是否赞过这篇极高（列表页、详情页）O(1) 判断成员是否存在，最好能一次查多篇
我赞过的文章（按时间）低按时间排序、分页

如果用数据库，需要建一张 likes(user_id, post_id, created) 表加唯一索引。列表页 10 篇文章，要执行 COUNT(*) GROUP BY post_id 和 WHERE user_id = ? AND post_id IN (…) 两个查询，并且点赞数据增长很快。

数据库里通常一张表加两个索引就能支持两个方向的查询。Redis 没有二级索引，所以要自己维护两个结构，代价是写入时必须同时修改两处，下面用 MULTI 事务保证这一点。

def post_likers(post_id):
    """SET  给这篇文章点过赞的用户 ID"""
    return _k('post', post_id, 'likers')


def user_likes(user_id):
    """ZSET  用户点赞过的文章：member = 文章 ID，score = 点赞时间戳"""
    return _k('user', user_id, 'likes')

为什么用 ZMSCORE 判断「是否赞过」

要判断「用户 3 是否赞过文章 1、2、3」，如果用文章维度的 SET，需要 3 次 SISMEMBER（每篇文章一个 Key）。用户维度的 ZSET 只有一个 Key，ZMSCORE（Redis 6.2+）一条命令就能查出多个文章的分数，返回 nil 的就是没赞过。

6代码实现

6.1 点赞 / 取消

def like(user_id, post_id):
    """点赞。返回 True 表示这次是新点赞，False 表示之前已经赞过（幂等）。"""
    pipe = get_redis().pipeline()
    pipe.sadd(K.post_likers(post_id), user_id)
    # NX：已经赞过的话不更新时间
    pipe.zadd(K.user_likes(user_id), {post_id: time.time()}, nx=True)
    added, _ = pipe.execute()
    return added == 1
def unlike(user_id, post_id):
    """取消点赞。返回 True 表示确实取消了，False 表示本来就没赞过。"""
    pipe = get_redis().pipeline()
    pipe.srem(K.post_likers(post_id), user_id)
    pipe.zrem(K.user_likes(user_id), post_id)
    removed, _ = pipe.execute()
    return removed == 1

6.2 批量读取

def attach_like_info(posts, user=None):
    """
    给一组文章设置 like_count 和 liked 属性，固定 1 次网络往返：
    N 个 SCARD + 1 个 ZMSCORE 放在同一个 pipeline 里。
    """
    posts = list(posts)
    if not posts:
        return posts
    pipe = get_redis().pipeline(transaction=False)
    for post in posts:
        pipe.scard(K.post_likers(post.id))
    if user is not None and user.is_authenticated:
        # ZMSCORE 一次查多个 member 的分数，没赞过的返回 None
        pipe.zmscore(K.user_likes(user.id), [post.id for post in posts])
    results = pipe.execute()
    liked = results[len(posts)] if len(results) > len(posts) else [None] * len(posts)
    for post, count, score in zip(posts, results, liked):
        post.like_count = count
        post.liked = score is not None
    return posts
transaction=False

只读操作不需要 MULTI/EXEC 的原子性，pipeline(transaction=False) 只是把命令打包发送，开销更小。写操作（like / unlike）需要两个结构一起修改，所以用默认的事务模式。

def liked_posts(user_id, count=20):
    """用户最近点赞的文章，按点赞时间倒序。"""
    ids = [int(i) for i in get_redis().zrevrange(K.user_likes(user_id), 0, count - 1)]
    posts = Post.published.in_bulk(ids)
    return [posts[i] for i in ids if i in posts]

8边界与思考

本实现的取舍
  • 点赞数据只存在 Redis：依赖 AOF 持久化（见设计文档「模式 C」）。生产环境通常会通过消息队列异步写入数据库，作为对账和恢复的依据。
  • 百万赞的文章：SET 中有 100 万个用户 ID 时大约占几十 MB，而且是大 Key。可以只用 SET 存最近的点赞用户，另外用 STRING 计数器存总数；「是否赞过」改为查用户维度的 ZSET。
  • MULTI 不是回滚事务：其中一条命令出错（比如类型错误），其他命令照样执行。它只保证这几条命令连续执行，中间不会插入其他客户端的命令。
思考题
