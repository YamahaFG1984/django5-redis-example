产品需求文档（PRD）

在现有博客上补齐一个内容社区常见的互动和运营功能，同时把这个项目做成学习 Redis 的教材。

版本 v1.0 状态：已评审 step-01-docs

1背景

1.1 现状

《Django 5 By Example》第 3 章完成后，博客已经具备：

  • 文章的发布、列表分页、详情页（PostgreSQL 存储，Post.published 管理器）；
  • 按标签筛选（django-taggit），基于共同标签的「相似文章」；
  • 评论、邮件分享、RSS、Sitemap、基于三元组相似度的全文搜索；
  • 侧边栏：文章总数、最新文章、评论最多的文章。

1.2 存在的问题

问题表现根因
读者互动少看不到浏览量、不能点赞、不能关注作者缺少互动功能
内容不好找只有「最新」和「评论最多」，没有热榜和个性化推荐缺少行为数据及其计算
每次请求都查库侧边栏 3 个查询、相似文章聚合查询，每个页面都要执行没有缓存层
容易被滥用评论、分享邮件接口可以被无限次调用没有限流
作者收不到反馈有新评论时作者不知道没有通知机制

1.3 为什么用 Redis

上面这些需求有几个共同点：写入频繁（每次浏览都要计数）、读取频繁（每个页面都显示）、对实时性有要求，同时能接受少量数据丢失（浏览量差几个不影响业务）。关系型数据库不擅长这类负载，Redis 是常见的选择：数据在内存里，单线程执行命令所以每条命令都是原子的，而且提供了多种数据结构，很多需求一两条命令就能完成。

2目标与非目标

目标

  • 实现 10 个基于 Redis 的功能，覆盖 STRING、HASH、LIST、SET、ZSET 五种基础结构，以及 HyperLogLog、Bitmap、Stream 和 Lua 脚本
  • 每个功能附带场景分析、选型理由、图示、代码、测试
  • 每个功能一个 git tag，可以逐步回放
  • 代码风格和原书保持一致，尽量少改原有代码

非目标

  • 前端美化与 SPA 化（模板只做最小改动）
  • Redis 集群 / 哨兵部署（只在文档中讨论）
  • 引入 Celery 等任务框架（直接用 Redis Stream 实现）
  • 完整的用户注册体系（用 Django 自带登录 + 演示账号）

5用户故事与验收标准

F1 文章浏览量

用户故事：作为读者，我想在文章页看到这篇文章被看过多少次、被多少人看过，以判断它是否值得读。

  • AC1 详情页展示「N 次浏览 · M 位读者」，列表页每篇文章展示浏览次数。
  • AC2 同一访客 30 分钟内反复刷新只计 1 次 PV。
  • AC3 UV 按访客去重（登录用户按用户 ID，匿名用户按 Session），允许 1% 以内误差。
  • AC4 浏览量定期回写数据库；Redis 数据丢失后，计数从数据库中的值继续累加，不会归零。

F2 热门排行榜

用户故事：作为读者，我想看到今天、本周、历史上最热的文章。

  • AC1 侧边栏展示「本周热门」前 5；独立页面 /blog/ranking/ 展示总榜、日榜、周榜各前 10，显示热度值。
  • AC2 热度 = 去重后的浏览次数，实时更新。
  • AC3 日榜数据只保留 8 天，过期自动清理。
  • AC4 下线或删除的文章不出现在榜单上。

F3 查询缓存

用户故事：作为运营，我希望访问量上涨时数据库压力不跟着线性上涨。

  • AC1 侧边栏数据、文章详情、相似文章走缓存，命中时不查库。
  • AC2 文章或评论变化后，相关缓存立即失效，读者看到的是新数据。
  • AC3 访问不存在的文章不会每次都穿透到数据库（缓存穿透）。
  • AC4 热点缓存过期瞬间只有一个请求回源（缓存击穿）；缓存过期时间带随机抖动（缓存雪崩）。

F4 点赞

用户故事：作为登录用户，我想给喜欢的文章点赞，也可以取消；我想看到自己赞过哪些文章。

  • AC1 每人对每篇文章最多点赞 1 次，重复提交结果不变（幂等）。
  • AC2 详情页展示点赞数，以及我是否已赞（按钮显示「点赞」或「取消点赞」）。
  • AC3 「我的点赞」页面按点赞时间倒序列出文章。
  • AC4 未登录用户点赞时跳转到登录页。

F5 每日签到

用户故事：作为登录用户，我每天来签到，想看到本月签到日历和连续签到天数。

  • AC1 每天只能签到 1 次，重复签到提示「今天已签到」。
  • AC2 页面展示本月日历（已签到的日期高亮）、本月签到天数、连续签到天数。
  • AC3 展示今日全站签到人数，以及最近 7 天每天都签到的人数。
  • AC4 连续签到跨月也能正确累计；展示累计签到天数和积分（每天 +1，连续 7 天额外 +5）。
  • AC5 存储开销：签到日历每用户每月不超过 4 字节。

F6 关注 & 时间线

用户故事：作为读者，我想关注喜欢的作者，并在一个页面按时间看到他们的新文章。

  • AC1 文章详情页可以关注或取消关注作者，展示作者的粉丝数。
  • AC2 作者发布文章后，所有粉丝的时间线立刻出现这篇文章。
  • AC3 新关注一个作者时，他最近的文章会补进我的时间线；取消关注后，他的文章从时间线移除。
  • AC4 时间线使用游标分页，翻页时有新文章发布也不会出现重复或遗漏。
  • AC5 展示我和某作者的共同关注。

F7 个性化推荐

用户故事：作为读者，我想看到和我兴趣相关、但我还没读过的文章。

  • AC1 根据我读过的文章的标签计算兴趣，按兴趣加权推荐。
  • AC2 推荐结果不包含已读文章。
  • AC3 新访客（冷启动）推荐结果用热榜补齐。
  • AC4 推荐结果缓存 60 秒，避免每次请求都重新计算。

F8 限流

用户故事：作为运营，我要防止有人用脚本刷评论、批量发分享邮件。

  • AC1 同一 IP 每分钟最多发 3 条评论（滑动窗口）。
  • AC2 同一 IP 每小时最多发 5 封分享邮件（固定窗口）。
  • AC3 超过限制返回 HTTP 429，并提示多少秒后可以重试。
  • AC4 计数在高并发下准确（原子操作）。

F9 搜索增强

用户故事：作为读者，我想知道大家都在搜什么，能快速重复自己之前的搜索，输入时有联想提示。

  • AC1 搜索页展示热搜榜前 10。
  • AC2 展示我最近的 10 条搜索，去重，最新的在前。
  • AC3 输入关键词前缀时，返回标题以该前缀开头的文章（最多 8 条）。

F10 评论通知

用户故事：作为作者，我想在有人评论我的文章时收到站内通知。

  • AC1 评论提交后立即返回，通知由后台进程异步处理，不阻塞用户。
  • AC2 侧边栏展示未读通知数，进入通知页后清零。
  • AC3 后台进程崩溃重启后，未处理完的消息不丢失，会被重新处理。
  • AC4 每个作者最多保留最近 50 条通知。

7非功能需求

维度要求实现方式
性能单次请求中所有 Redis 操作合计 < 5ms使用 pipeline 合并命令、MGET 批量读取，避免循环里逐条请求
原子性计数、限流在并发下准确依赖 Redis 单线程执行命令；多条命令用 Lua 或 MULTI 包装
内存所有临时数据都要设过期时间Key 规范中写明 TTL，测试里断言 TTL
可靠性Redis 数据丢失不影响核心阅读功能浏览量回写数据库；索引类数据提供 rebuild 命令
可测试性每个功能有自动化测试测试使用独立的 Redis DB，每个用例前清空
可读性代码适合教学每个功能一个 service 模块，所有 Key 集中定义在 redis_keys.py
